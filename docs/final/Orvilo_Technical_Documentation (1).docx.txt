1. Introduction
1.1 Purpose of this document
This document is the complete technical reference for Orvilo, a system that lets a wallet owner express guardrails for an autonomous AI wallet agent in natural language and then enforces those guardrails with deterministic, verifiable controls. It describes what the repository contains today: the architecture, the data flow, the algorithms and calculations, the HTTP API, the user interface, operating procedures, test evidence and the boundaries of the current implementation.
Every statement describes software that is present in the repository. Where behaviour is simulated rather than executed on a live blockchain, the text says so explicitly, and Section 3.4 summarises the status of every major capability in one table.

2. Executive summary
2.1 The problem and the approach
Autonomous agents that can move funds are only as safe as the limits placed on them. Limits written in code are hard for a wallet owner to read; limits written in plain language are easy to read but ambiguous. Orvilo bridges the gap. The owner writes an instruction such as “buy ETH when gas is under 20 gwei and never let the balance fall below $500”, and the system turns it into a typed policy that both humans and machines can check.
Two independent readers interpret the instruction. A deterministic rule reader produces a typed abstract syntax tree (AST); an optional schema-constrained LLM reader produces a second one. The policy package type-checks both, compares them formally with the Z3 solver, produces a canonical human-readable readback and a SHA-256 identifier, and exports guard parameters. Only then can the owner approve and deploy the policy.
Once a policy is active, the autonomous agent observes market state, retrieves similar historical regimes, proposes an intent, performs a dry run and applies deterministic gates before any change is made to the local wallet ledger. Blocked attempts are recorded with the reason, so every outcome is auditable.

2.3 What the repository is - and is not
The default application is a local deterministic simulation. It does not sign or broadcast transactions, and the Solidity contract is a deployable reference rather than evidence of a deployed contract. This boundary is repeated wherever it matters in the sections that follow, because it determines how the test and attack-tester results should be interpreted.

The default application is a local Flask simulation. It uses JSON files, in-memory policy and security state, optional Coinbase and Ethereum RPC observations, and a Python contract model. The default flow does not sign or broadcast transactions. The Solidity contract is a deployable reference, not evidence of a deployed contract.

3.3 Worked scenario
The owner submits a policy, reviews its readback, approves it and deploys it through the dashboard. The agent watches gas. When gas satisfies the trigger, the reasoning pipeline retrieves a regime, simulates a swap and checks the reserve floor. The attempt then ends one of two ways: Orvilo records a locally confirmed swap, or it records a blocked attempt together with the reason.

5. System architecture and data flow
5.1 Architectural style
Orvilo is a modular monolith. Flask routes coordinate the policy, agent, reasoning, exchange, contract and user modules inside one Python process. This keeps local demonstrations simple while preserving explicit module boundaries that can later be deployed behind a WSGI server and a production persistence layer.
 Five horizontal layers: presentation, API and orchestration, domain modules, persistence, and external boundary. 

Figure 2. Layered view of the application.
5.2 Request lifecycle
1. The browser requests dashboard state and sends user actions to JSON endpoints.
2. The server validates inputs and delegates to the relevant domain module.
3. Domain modules update local state and return a structured result.
4. The UI refreshes its panels, or consumes market updates through server-sent events.
5. Assistant requests use the same action surface; confirmation is required for pause operations.
5.3 Concurrency model
The agent loop, the Coinbase listener and the gas oracle run as daemon threads. Each JSON-backed service guards reads and writes with a re-entrant lock. Writes are whole-file rewrites performed while the lock is held, which is adequate for a single-process demonstration but is not a substitute for database transactions.

8.2 Autonomous tick
Each scheduled tick evaluates task state and market inputs. A triggered task retrieves relevant regime context, forms an intent, computes a dry-run result, evaluates the deterministic safety gates, performs EVM-style preflight decoding, and persists either an execution record or a blocked explanation. The sequence is shown in the agent runtime figure in Section 7.3.
Dry-run calculations include balance impact, slippage, gas cost, reserve floor, transaction cap, daily cap and allowlist checks. The exact formulas are in Section 11.
8.3 Attack test
1. The operator lists the available vectors (GET /api/contract/attack-test/*).
2. The operator runs one vector by id (POST /api/contract/attack-test/*).
3. The guard model evaluates pause state, operator, policy hash and caps in order.
4. The result returns the named modeled revert, a gas estimate and a status. Local state is not mutated.
Reading attack-test results
Local attack-test results represent modeled contract rejections. They are not live Base Sepolia transaction receipts and must not be cited as on-chain evidence.
	

8.4 Manual intent validation
POST /api/validate_intent accepts a trade size and gas price and returns the guard result. With execute set, an allowed intent mutates the local JSON ledger only; no transaction is submitted anywhere.

10.7 Example requests

11. Business rules, algorithms and calculations
This section defines every numeric rule that affects whether an action is allowed. The worked examples use illustrative inputs; the ETH price and gas values are taken from the dashboard screenshots in Section 13.
11.1 Reserve and cap guards
For a proposed USD trade T, current USDC balance B, reserve floor F, per-transaction cap C, daily spend so far S and daily cap D, the local checks are:
GUARD CONDITIONS
B − T  ≥  F
T  ≤  C
S + T  ≤  D
	

Inputs come from wallet JSON, policy parameters and the proposed task. Values use Python floats in the wallet and simulator layers; policy compilation itself uses exact Fraction values and Z3 reals.

11.2 Dry-run swap
Base slippage is 0.05 %. If gas exceeds 40 gwei, 0.15 percentage points are added. With market price P, slippage s (in percent) and gas in gwei:
DRY-RUN FORMULAS
effective_price = P × (1 + s / 100)
estimated_ETH   = T / effective_price
post_swap_USDC  = B − T
	

The simulator rounds ETH to five decimals, USDC to two, and report fields to their model precision. A regime is classified high-risk when the risk score is at least 7, the expected return is below −2 %, the risk level is HIGH, or the recommendation is HALT_TRADING.

11.3 RAG scoring
Each historical regime receives a weighted score and the highest-scoring regime is returned:
REGIME SIMILARITY
score = 0.45 × gas_compat + 0.35 × price_range + 0.20 × scenario_trend
	

Example: gas compatibility 0.90, price-range score 0.80 and scenario/trend score 0.50 give 0.45 × 0.90 + 0.35 × 0.80 + 0.20 × 0.50 = 0.785.

11.4 Daily contract accounting
The Solidity reference computes the day index from the block timestamp and resets the daily counter whenever the day changes. It then rejects a call if the proposed cumulative total would exceed the daily cap.
DAILY CAP LOGIC
dayIndex = block.timestamp / 1 days
if dayIndex changed:  spentTodayUsd = 0
reject if  spentTodayUsd + amount > dailyCapUsd
	

In the default run this behaviour is represented by simulator inputs, not by a deployed chain.

14. Authentication and authorization
Not for public deployment
No login, session, bearer token, CSRF protection or route authentication is implemented. Do not expose the default server to an untrusted network or use it with real funds.
	

The UI is intended for local demonstration. Application-level labels identify owner, reviewer and agent, while the contract reference code has owner and operator modifiers. The Python client does not cryptographically authenticate requests.

Smoke checks
curl -fsS http://127.0.0.1:5001/api/market/live
curl -fsS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:5001/
	

The first call should return a JSON market snapshot and the second should print 200. The application initializes local JSON files when they are absent; there are no migrations to run.
15.4. Docker Deployment
Build the Docker image from the repository root:
docker build -t orvilo:latest .
Run the application:
docker run -d \
  --name orvilo \
  --restart unless-stopped \
  -p 5000:5000 \
  orvilo:latest

Verify the deployment:
docker ps

docker compose down
Stop and remove the container:

The default Docker configuration uses the offline mock LLM and does not require an API key. Optional LLM and blockchain settings can be configured through environment variables.
