1. Executive summary
Orvilo is a simulation-first Flask application that converts natural-language trading constraints into a typed policy, compares deterministic and LLM-derived interpretations, applies Z3-backed checks, records a human-review workflow, and runs a local autonomous task loop. It includes a Solidity reference contract named PolicyWallet with owner/operator authorization, policy hashes, token and recipient allowlists, spending caps, reserve floors, pause, and allowance-revocation functions.
The assessed deployment is local simulation by default. The Docker image sets LLM_PROVIDER=mock; the application uses JSON state and the contract client returns generated transaction identifiers instead of signing and broadcasting transactions. The configured network is Base Sepolia (84532), but no genuine on-chain transaction hash, receipt, signer operation or deployed-contract state was verified in this assessment.

1.1 Overall verdict
Not suitable for real funds without remediation
Orvilo works as a policy-verification and simulation tool. Its safety controls are not yet an enforcement boundary: the HTTP API has no authentication, the reference contract trusts caller-supplied financial values, and the default client produces generated rather than cryptographic transaction identifiers.
Findings K-01 to K-08 must be closed, with the retest evidence listed in Section 17, before any deployment that handles real value or is reachable beyond a trusted local machine.

	1.3 Principal risks
* Unauthenticated administrative routes (K-01). Wallet-mutating and policy-administering routes can be called by any client that reaches the server.
* Unsafe contract execution design (K-02). Execution accepts caller-supplied USD and post-balance values and performs arbitrary router calls.
* Synthetic approvals and hashes (K-03, K-04). Default signing and approval are generated strings, and deployment can proceed before review.
* Fallbacks that look like success (K-06). Simulated execution can appear successful when RPC or deployment state is unavailable.
1.4 What is working well
* Deterministic policy parsing, type-checking and Z3 comparison are covered by the passing test suite.
* The Solidity reference contract contains meaningful guards: owner/operator modifiers, policy-hash check, allowlists, per-transaction and daily caps, reserve floor, pause and revocation.
* The Docker image runs as a non-root user, excludes .env from the build context and defines a health check.
* Simulation boundaries are clearly documented, and the agent runtime enforces a single active task with pause/resume controls.

	8. Authentication, authorization, and account isolation
No login, session, bearer token, API key, wallet-signature challenge, CSRF protection or per-account ownership check was found in flask/server.py. The following route groups are callable by any client that can reach the Flask server:
* Wallet mutation and transaction creation
* Reset of simulation state
* Policy review, approval and deployment
* Pause and unpause; operator revocation; allowance revocation; policy invalidation
* Agent pause and resume
* Assistant actions


Interpretation
The application is a single-user local simulation, which explains the design, but that boundary must not be mistaken for authorization. If exposed beyond a trusted local machine, the API permits unauthorized state changes and cross-user access by construction.

	9.1 Weaknesses in the approval path
* The workflow permits deploy_policy from DRAFT, REVIEWED or DEPLOYABLE, despite the documented human-in-the-loop intent.
* Approval signatures are generated strings when no signature is supplied.
* There is no authenticated binding between reviewed_by/approved_by and a key, no expiry, no nonce and no immutable approval payload.
* There is no verified pre-submission chain-state reconciliation in the default path.
10. Autonomous agent and tool security
The agent has a single-task constraint and pause/resume controls. These are useful safety mechanisms and were exercised by the Docker smoke test. They are not an authorization boundary because the controlling routes are unauthenticated and JSON task state is writable by the application process.
The LLM is described as untrusted and is compared with deterministic parsing. This reduces interpretation risk, but it does not protect against:
* Unauthorized API invocation.
* Malicious market or RPC responses.
* A future tool being granted broader credentials.
Prompt injection and malicious external content were not subjected to a dedicated adversarial test campaign.

	11.2 Material weaknesses
Critical design concern (K-02)
executeSwap accepts an arbitrary router and arbitrary routerData, then executes router.call. The contract does not constrain the router to an approved address, does not independently derive USD value or post-trade balance, and does not enforce the returned amount against minAmountOut after the arbitrary call.
executeTransfer also trusts caller-provided USD and balance values.
	

The reviewed source is a reference contract, not proof of the bytecode at the configured address. No deployment artifact, verified source match, transaction receipt or live owner/operator state was supplied.

	12.2 Gaps not established by the implementation
* Token-decimal correctness for arbitrary ERC-20 tokens.
* Oracle freshness and signed price provenance.
* Slippage enforcement at the contract boundary.

13. Application, API, and data security
The code uses JSON request parsing and typed conversions, but broad input validation is inconsistent. The application stores wallet and agent task state in local JSON files and uses in-process locks; this is not a durable transaction boundary for multiple workers or concurrent deployments. The reset endpoint deletes and reinitializes simulation state without authentication.

	14. Infrastructure, dependencies, and external services
14.1 Positive baseline controls
* Dockerfile uses Python 3.13 slim.
* Runs as non-root user orvilo.
* Excludes .env and generated artifacts through .dockerignore.
* Defines a container health check.

16.3 Detailed findings
K-01
	Unauthenticated HTTP administrative and wallet mutation routes
	CRITICAL
	Description
	No login, session, bearer token, API key, wallet-signature challenge, CSRF protection or per-account ownership check exists in flask/server.py. Routes for wallet mutation, transaction creation, reset, policy review/approval/deployment, pause/unpause, operator and allowance revocation, policy invalidation, agent pause/resume and assistant actions accept requests from any client that can reach the server.
	Impact
	Any reachable client can alter wallet state, approve and deploy policies, or disable safety controls. Application permission labels give no protection at the HTTP boundary.
	Recommendation
	Add authentication and role-based authorization middleware; add CSRF protection, TLS/reverse proxy and rate limits before any exposure; block public deployment until complete.
	Retest evidence
	Authenticated negative tests for every mutating route and a role matrix test (owner, reviewer, operator, anonymous).
	Status
	Open
	

K-02
	Contract trusts caller-supplied financial values and arbitrary router calls
	CRITICAL
	Description
	executeSwap accepts an arbitrary router and routerData and executes router.call. USD value and post-balance are caller inputs in both executeSwap and executeTransfer. The returned amount is not enforced against minAmountOut after the call.
	Impact
	A caller within the operator role can bypass per-transaction caps, daily caps and the reserve floor by supplying false values, or route funds through an unapproved contract.
	Recommendation
	Restrict routers and calldata to an allowlist; derive or oracle-attest amounts; validate token decimals; enforce minAmountOut; add replay protection; obtain an independent Solidity audit.
	Retest evidence
	Contract review addressing arbitrary calls and caller-supplied values; deployed bytecode/address match; fuzz and malformed-calldata tests.
	Status
	Open
	

K-03
	Default client fabricates transaction hashes and confirmations
	HIGH
	Description
	The contract client creates UUID-derived strings prefixed with 0x as tx_hash. No signer is loaded in the default path.
	Impact
	Users and auditors may treat generated identifiers as proof of on-chain execution.
	Recommendation
	Introduce a real signer boundary with chain-ID/domain separation, nonces and receipt verification; define explicit states: unavailable, simulated, submitted, pending, confirmed, reverted.
	Retest evidence
	Genuine Base Sepolia receipts with signer and nonce evidence.
	Status
	Open
	

K-04
	Workflow accepts unauthenticated approvers and synthetic signatures
	HIGH
	Description
	reviewed_by and approved_by are free-text fields; approval signatures are generated strings when none is supplied; deploy_policy is permitted from DRAFT, REVIEWED or DEPLOYABLE.
	Impact
	The human-in-the-loop guarantee can be bypassed by any caller, and approvals cannot be attributed to a real person.
	Recommendation
	Require authenticated reviewer/approver roles; use cryptographic approval over an immutable policy hash and parameters; reject deployment from DRAFT and REVIEWED.
	Retest evidence
	Tests proving deployment is rejected without a valid signature from an authorized approver.
	Status
	Open
	

K-05
	Shared JSON state has no account isolation or durable transactions
	HIGH
	Description
	Wallet and task state live in local JSON files guarded by in-process locks. There is no account identity, row-level authorization, migration system or durable transaction boundary.
	Impact
	Cross-user access by construction; lost updates with multiple workers; no reliable audit record.
	Recommendation
	Move to a transactional store with account ownership, row-level authorization, durable audit records, idempotency keys, and migration/backup procedures.
	Retest evidence
	Two-account isolation test (ST-09) and concurrent-write tests.
	Status
	Open
	

K-06
	Fallbacks can return simulated success when live state is unavailable
	HIGH
	Description
	RPC and deployment failures fall back to simulated or deterministic results in contracts/simulator.py.
	Impact
	Operators may believe an action succeeded on-chain when it did not.
	Recommendation
	Fail closed on uncertainty and label simulated results unambiguously; never report CONFIRMED for a generated identifier.
	Retest evidence
	Dependency-failure tests showing explicit failure states.
	Status
	Open
	

K-07
	No nonce, replay or expiry binding
	HIGH
	Description
	The reviewed execution functions have no on-chain nonce or replay domain, and approvals have no expiry, nonce or immutable payload.
	Impact
	Previously valid approvals or executions could be reused.
	Recommendation
	Add nonces, expiry and domain separation to executions and approvals.
	Retest evidence
	Replay and duplicate-submission tests.
	Status
	Open
	

K-08
	No rate limiting, CSRF protection, TLS or production WSGI boundary
	HIGH
	Description
	The Docker image runs Flask’s development server on a published port with no TLS, CSRF protection, rate limiting or request-size policy.
	Impact
	Exposure to abuse, forged requests and traffic interception if reachable beyond a trusted machine.
	Recommendation
	Deploy behind a production WSGI server and TLS-terminating reverse proxy with rate limits and CSRF protection.
	Retest evidence
	Configuration review and negative tests for oversized and forged requests.
	Status
	Open
	

K-09
	Market/RPC fallback and default addresses are not proof of live state
	MEDIUM
	Description
	WebSocket and RPC failures use synthetic values; the contract address is a client default not tied to a verified deployment.
	Impact
	Decisions may be based on synthetic data, and the configured address may not match deployed code.
	Recommendation
	Surface data provenance and freshness; verify and pin deployment addresses.
	Retest evidence
	Bytecode match for the configured address and provenance checks in tests.
	Status
	Open
	

K-10
	No dependency scan, bytecode match or live receipt evidence
	MEDIUM
	Description
	No scanner result, deployed bytecode comparison or live receipt was available to the assessment (ST-06, ST-12).
	Impact
	Unknown vulnerable dependencies and unverified deployment.
	Recommendation
	Add dependency scanning to CI; verify deployed source; capture live receipts.
	Retest evidence
	Scanner report, verified source match and receipts.
	Status
	Open
	

Residual exposure
These are residual exposure items, not claims that a live mainnet exploit occurred. The application is explicitly simulation-first; the risk is that simulated controls or identifiers could be mistaken for production-grade authorization and settlement.

2. Pause the contract.
3. Invalidate the policy.
4. Rotate credentials.

19. Assessment conclusion and limitations
Orvilo demonstrates a useful policy-verification and simulation workflow, and its local automated tests and Docker smoke test pass. The repository also contains meaningful reference guardrails in the Solidity contract and clear simulation boundaries in documentation.
Conclusion
The evidence does not support a conclusion that Orvilo is safe for real funds or internet exposure. Authentication, account isolation, real signing, live deployment verification, replay protection, trusted financial valuation and production monitoring remain unresolved.

This is a self-assessment of the repository and local execution. It is not an independent audit, formal verification certificate, penetration test or deployment attestation.
