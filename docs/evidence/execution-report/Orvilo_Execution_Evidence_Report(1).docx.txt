1. Executive Summary
This report records what the Orvilo software actually did when its policy-guard, workflow and revocation logic was executed in an isolated sandbox on 19 October 2026. It documents seven execution scenarios, the automated regression suite, the evidence log and its integrity checksum, and it states plainly where the evidence stops.

Headline findings
* Guardrails behave as designed in the simulator. A compliant $200 transfer was accepted; a $700 transfer, a transfer to a non-allowlisted address and any transfer while paused were each rejected with the correct, named error (EE-01, EE-02, EE-03, EE-05).
* The approval workflow progresses through all four states. A proposal moved DRAFT → REVIEWED → DEPLOYABLE → ACTIVE (EE-04), although approver identities and signatures are not authenticated.
* All six modeled attack vectors were rejected. Recipient, token drain, balance-floor drain, daily-limit bypass, pause breach and unauthorized-operator vectors returned the expected reverts (EE-07).
* One control failed. After an operator was revoked, the Python execution path still returned a synthetic CONFIRMED result (EE-06). This is disclosed as an open implementation gap.
* No on-chain evidence exists. Nothing was signed or broadcast, so no transaction hashes, receipts or block data are claimed.


SUBMISSION CLASSIFICATION
The defensible category is non-on-chain sandbox evidence. Although the application labels its network Base Sepolia (chain ID 84532), the default client generates UUID-based hash-like identifiers and does not sign, submit, poll or verify blockchain transactions.
	

2. Purpose, Scope and Method
2.1 Purpose
This report records repeatable execution evidence for the current Orvilo repository. It demonstrates implemented policy-guard evaluation, workflow state transitions, simulated attack rejection, emergency pause behavior and permission revocation behavior. The evidence is intended to show what the software actually did in the assessed sandbox, not what a future production deployment is expected to do.


2.2 Scope
Covered
	Excluded or unavailable
	* Authorized operation accepted by local policy guards
* Per-transaction limit and recipient allowlist rejection
* Draft, review, approval, deployable and active workflow transitions
* Emergency pause rejection and six modeled adversarial checks
* Post-revocation execution attempt, including the observed enforcement gap
* Repository automated tests (90 passed)
	* Genuine private-key signing
* Transaction submission, receipts and block inclusion
* Deployed bytecode verification
* Live account balances
* Production authentication and multi-user account isolation
* Mainnet execution
	2.3 Evidence method
The evidence was produced by a dedicated generator script rather than by hand, so every scenario can be re-run and checked against the sealed log.
 fig_pipeline.png 

Figure 1. Evidence production pipeline, from generator script to sealed log to this report.


1. The generator creates fresh in-memory objects for each scenario, so no earlier state can leak into a later result.
2. It deliberately avoids the mutable repository JSON stores and the Flask routes. This preserves existing wallet and task state and prevents sandbox activity from being confused with chain settlement.
3. RPC is disabled through an explicit offline Web3 stub, and the LLM runs in its default mock/offline mode.
4. Each record is written to a structured JSON log with an ISO 8601 UTC timestamp, scenario ID, inputs, expected and observed results, before/after state, outcome and a LOCAL_SANDBOX_SIMULATION label.
5. A SHA-256 checksum of the log is generated, and the repository regression suite is run separately.

WHY THIS SCENARIO FAILED
The revocation flag was updated correctly (true → false), but the Python execution method selected a local sender without consulting that flag and returned a synthetic CONFIRMED response. The expected rejection did not occur, so this scenario is recorded as failed.

The Solidity source restricts execution to authorized callers (onlyAuthorized), but that contract was not compiled, deployed or exercised in this run, so the gap is confirmed only for the Python execution path.

Primary limitations
* The Python wallet client fabricates confirmation data instead of signing and broadcasting.
* The local revocation flag is not consulted by the Python execution method.
* Workflow reviewers, approvers and signatures are strings rather than authenticated cryptographic approvals.
* The simulator can fall back to success-oriented estimates when RPC is unavailable; this report disables RPC and labels the result accordingly.
* The reference contract was not compiled, deployed, bytecode-matched or exercised in this run.
* No production account credentials were available, and the demonstration video records sandbox behavior only.

	15.2 Reproduction

	Appendix C · Interpretation Rule


Throughout this report, ‘simulated success’ means a local method returned a successful simulation result. ‘Synthetic confirmation’ means the application constructed confirmation-like fields locally. Neither term means a blockchain accepted or finalized a transaction. Only a genuine receipt from the identified chain, reconciled to the intended state change, would support that conclusion.
